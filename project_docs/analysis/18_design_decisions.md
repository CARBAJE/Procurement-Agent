# Design Decisions

This document records the key architectural and implementation decisions made during Phases 1–3 of the Procurement Agent on Beckn Protocol. Each entry covers context, the decision taken, concrete rationale, and its consequences. Where a formal ADR exists it is cited; otherwise the evidence trail points to the implementation deviations record or code findings.

---

## ADR-0001: Redis Pub/Sub for Async Beckn Discovery

**Status:** Accepted — May 2025

**Context:**
Beckn Protocol v2.0.0 makes discovery inherently asynchronous. A `POST /discover` to the ONIX adapter returns only an ACK; the actual catalog arrives later as a separate `on_discover` webhook callback. The IntentParser MCP sidecar needs to fire a discover request and then hand a synchronous result back to the IntentParser pipeline. Without decoupling, the straightforward implementation holds the HTTP connection open while waiting for the callback, which blocks the asyncio event loop and creates a deadlock: the sidecar is suspended awaiting the callback while the callback itself must be processed by the same event loop.

(Source: `docs/architecture/decisions/0001-use-redis-pubsub-for-async-beckn-responses.md` -- Confidence: High)

**Decision:**
Use Redis Pub/Sub on per-transaction channels named `beckn_results:{transaction_id}`. The MCP sidecar subscribes to the channel **before** firing the discover request, fires the request as a non-blocking `asyncio.create_task` (not `await`), then blocks on the Redis subscriber with a configurable timeout (`REDIS_RESULT_TIMEOUT`, default 15 s). When `beckn-bap-client` receives the `on_discover` callback, its handler publishes the normalized catalog payload to the same Redis channel. The sidecar's subscriber unblocks and returns the catalog to IntentParser Stage 3.

**Rationale:**
- Breaks the deadlock by decoupling the two coroutines across an external message channel.
- Redis was already a required dependency (ONIX adapter uses Redis for its internal cache), so no new infrastructure is introduced.
- The channel name embeds `transaction_id`, providing natural isolation between concurrent discovery probes.
- Observable at any time via `redis-cli subscribe beckn_results:<uuid>`.
- Three alternatives were considered and rejected: HTTP polling (adds latency and requires server-side state), direct callback injection (inverts the dependency graph and introduces a circular import), in-process `asyncio.Queue` (breaks the microservices boundary — the MCP sidecar and beckn-bap-client are separate processes).

**Consequences:**
- Positive: Deadlock eliminated; producer/consumer fully decoupled; no new infrastructure.
- Negative: Redis becomes a hard runtime dependency for IntentParser Stage 3. If Redis is unavailable, the sidecar degrades to `{"found": false, "items": []}` rather than raising an error.
- Negative: Two code paths now handle the same `on_discover` event — the Redis publish path (for the MCP sidecar) and the `CallbackCollector.handle_callback` path (for the orchestrator). Both must be maintained in sync.
- Negative: `transaction_id` must be pre-generated by the caller and passed into the discover request so the Redis channel name is known before the subscription is opened.
- Neutral: `REDIS_RESULT_TIMEOUT` (15 s) is the effective latency ceiling for all discovery probes. `MCP_BAP_TIMEOUT` (default 8 s) governs only the HTTP fire-and-forget task, not the meaningful end-to-end deadline.

**The anti-pattern this prevents:**
`await`ing the discover POST inside the MCP sidecar reintroduces the deadlock. CLAUDE.md explicitly prohibits this: "Don't `await` the `/discover` POST in the MCP sidecar. It's `asyncio.create_task(...)`; blocking re-introduces the deadlock ADR-0001 was written to fix."

(Source: `docs/architecture/decisions/0001-use-redis-pubsub-for-async-beckn-responses.md` -- Confidence: High)
(Source: `services/mcp-sidecar/README.md` -- Confidence: High)
(Source: `services/beckn-bap-client/README.md` -- Confidence: High)

## pgvector Instead of Qdrant

**Status:** Implemented as-built deviation from spec.

**Context:**
The original design called for a Qdrant self-hosted vector database (preferred) or Pinecone managed (alternative) with a pgvector mirror for DR/audit purposes. Embedding vectors were specified at 3072 dimensions using the OpenAI `text-embedding-3-large` model. The system requires two vector stores: a BPP catalog semantic cache for IntentParser Stage 3 ANN validation, and an agent memory store for time-decayed supplier loyalty scoring.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)

**Decision:**
Use pgvector exclusively, with no Qdrant deployment. Two tables serve the vector workload:

- `bpp_catalog_semantic_cache` (migration `18_bpp_catalog_semantic_cache.sql`) — `vector(384)`, HNSW cosine, used by IntentParser Stage 3.
- `agent_memory_vectors` (migration `22_agent_memory_vector_dim.sql`) — `vector(384)`, HNSW cosine `ef_search=100`, used by orchestrator for supplier memory.

**Rationale:**
- The pilot corpus is below 100,000 records, a regime where pgvector HNSW is computationally equivalent to Qdrant HNSW in both latency and recall.
- Eliminating Qdrant removes one container, one StatefulSet, one backup strategy, and one infra dependency.
- PostgreSQL (with pgvector) was already the primary datastore; vector operations execute inside the same ACID-transactional connection pool, enabling atomic writes of both relational data and embedding vectors.
- Nightly ETL from PostgreSQL to Qdrant (described in spec) is rendered unnecessary.

**Consequences:**
- Positive: Simpler deployment, one fewer external service, lower total resource consumption.
- Positive: Vector writes and FK-dependent relational writes are atomic within one transaction.
- Negative: At scale beyond ~500K vectors, pgvector HNSW recall and query throughput will degrade relative to a purpose-built ANN engine such as Qdrant. Phase 4 should re-evaluate if the corpus grows.
- Negative: `KnowledgeBase/project_scaffold/ai_models/data_dictionary_er_model.md` still documents `AgentMemoryVector` with `VECTOR(3072)` and `text-embedding-3-large` — these are spec-era values. Engineers reading that document will see incorrect types.
- Known bug: `database/sql/00_extensions_and_types.sql` defines `embedding_model_type` ENUM with only `'text-embedding-3-large'` and `'e5-large-v2'`. The actual deployed models (`all-MiniLM-L6-v2`, `BAAI/bge-small-en-v1.5`) are absent, and `BAAI/bge-small-en-v1.5` is not added by any migration. Any INSERT that stores the actual model name in a column constrained by this ENUM will fail.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)
(Source: `database/sql/22_agent_memory_vector_dim.sql`, code findings -- Confidence: High)
(Source: `services/data-normalizer/README.md` -- Confidence: High)

## Local LLMs (qwen3:8b / qwen3:1.7b) Instead of GPT-4o

**Status:** Implemented as-built deviation from spec.

**Context:**
The original design specified GPT-4o as the primary LLM for intent classification and BecknIntent extraction, with GPT-4o-mini for lightweight/simple queries. Claude Sonnet 4.6 was described as a fallback for intent parsing. Using cloud-based LLM APIs introduces per-call cost, network latency, data egress of procurement data to a third-party API, and dependency on external service availability.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)

**Decision:**
Replace GPT-4o with `qwen3:8b` (primary, complex queries) and GPT-4o-mini with `qwen3:1.7b` (lightweight, simple queries), both served locally via Ollama (`OLLAMA_BASE_URL=http://localhost:11434/v1`). Claude Sonnet 4.6 is retained as a last-resort broadening fallback in IntentParser Stage 3 only (opt-in, requires `ANTHROPIC_API_KEY`), used solely when a query fails to match the BPP catalog and a broadened query re-attempt is needed.

Complexity routing is implemented in `IntentParser/orchestrator.py`: queries longer than 120 characters, containing two or more numeric tokens, or containing procurement-domain keywords are routed to `COMPLEX_MODEL` (`qwen3:8b` locally, `qwen3:1.7b` in the Docker container — see the Docker override note below).

**Rationale:**
- Zero per-call cost: Ollama serves models from local GPU/CPU, eliminating API billing entirely.
- Offline capability: the pipeline functions without internet access.
- Data sovereignty: procurement request content (item names, quantities, budgets, locations) never leaves the developer machine.
- Quality sufficient: structured JSON extraction with `instructor` Mode.JSON and `max_retries=3` achieves the required accuracy using qwen3 models for the constrained BecknIntent schema.

**Docker override (important discrepancy):**
`docker-compose.yml` sets `COMPLEX_MODEL=qwen3:1.7b` for the `intention-parser` container, overriding the code default of `qwen3:8b`. This collapses the two-tier routing — the dockerized service uses `qwen3:1.7b` for all queries regardless of complexity. No documentation in `docker-compose.yml` explains the rationale (likely a memory constraint on the developer host running Ollama). The complexity-routing logic is only active when IntentParser is run locally outside Docker.

**Consequences:**
- Positive: Zero LLM cost, offline operation, data sovereignty.
- Positive: `instructor` retry loop handles qwen3 JSON non-conformance without code changes.
- Negative: qwen3 models are less capable than GPT-4o on ambiguous or multi-constraint procurement queries. Stage 3 recovery (Claude broadening fallback) exists as a safety net but requires `ANTHROPIC_API_KEY`.
- Negative: The Docker container silently degrades to qwen3:1.7b for all queries; there is no warning or metric indicating that complex queries are not reaching the larger model.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)
(Source: `IntentParser/config.py`, code findings -- Confidence: High)
(Source: `docker-compose.yml` lines 14–15, code findings -- Confidence: High)

## Outbox Pattern for ERP PO Push (No Kafka)

**Status:** Implemented as-built deviation from spec.

**Context:**
The design specified Apache Kafka as the central event bus for ERP integration: PO creation events published to a Kafka topic, consumed by an ERP sync worker that pushes to SAP S/4HANA or Oracle ERP Cloud. Kafka provides durable, replayable, multi-consumer event streaming with configurable retention and replication. Deploying a Kafka broker adds operational complexity (KRaft configuration, topic management, consumer group offsets, storage provisioning).

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)

**Decision:**
Replace the Kafka publish/consume pattern for PO push with a PostgreSQL transactional outbox. The `erp_sync_records` table (migration `19b_erp_sync_records_outbox.sql`) acts as the outbox. The orchestrator writes a row to `erp_sync_records` within the same database transaction that creates the `purchase_orders` row. A background worker in `erp-adapter` polls `erp_sync_records WHERE status = 'pending'` using `FOR UPDATE SKIP LOCKED`, pushes the PO to the vendor ERP, and updates the row's status. A `kafka_offset` BIGINT column and `splunk_indexed` BOOLEAN column are pre-wired as placeholders for future Kafka and SIEM integration.

**Rationale:**
- Kafka broker not yet deployed in Phases 1–3; the outbox pattern is operationally equivalent for single-broker scenarios and requires no new infrastructure.
- Atomic guarantee: if the PO write to PostgreSQL succeeds, the outbox row is guaranteed to exist (same transaction). With Kafka, the PO could be committed to PostgreSQL while the Kafka publish fails, leaving the systems out of sync.
- FOR UPDATE SKIP LOCKED provides safe concurrent worker execution without a separate job queue service.
- `kafka_offset` placeholder makes the migration to Kafka non-breaking: the worker simply populates the column when a real Kafka producer is wired in Phase 4.

**Consequences:**
- Positive: Atomic write + queue in a single transaction. No Kafka broker dependency in Phases 1–3.
- Positive: Worker retry with exponential backoff (`5, 30, 120, 600, 3600` second schedule, per erp-adapter README) and dead-letter queue replay via `POST /api/v1/admin/outbox/{sync_id}/replay`.
- Positive: `GET /readyz` exposes outbox lag as a health signal.
- Negative: The outbox worker polls on a configurable interval (`WORKER_POLL_INTERVAL_SECONDS`, default 2 s) instead of being event-driven, introducing up to 2 s of additional PO-push latency after confirmation.
- Negative: In-process PostgreSQL outbox does not support multi-consumer fan-out (e.g., simultaneously pushing to SAP and triggering a Slack notification). Phase 4 Kafka migration is required when multiple independent consumers are needed.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)
(Source: `services/erp-adapter/README.md` -- Confidence: High)
(Source: `database/sql/19b_erp_sync_records_outbox.sql` -- Confidence: High)

## DeDi Registry Bypass (`targetType: url`)

**Status:** Feature beyond spec, implemented in Phase 1.

**Context:**
Beckn Protocol's standard network topology uses a DeDi (Decentralised Distributed) registry to resolve BPP endpoints. A BAP performing discovery would query the DeDi registry to obtain the target BPP's ONIX caller URL. In the local Docker Compose development environment, no DeDi registry is deployed or accessible. Routing all Beckn traffic through a live registry would require external network access and registration of the local BPP.

(Source: `config/README.md` -- Confidence: High)

**Decision:**
Set `targetType: url` in all four ONIX routing YAML files (`config/generic-routing-BAPCaller.yaml`, `config/generic-routing-BAPReceiver.yaml`, `config/generic-routing-BPPCaller.yaml`, `config/generic-routing-BPPReceiver.yaml`). This instructs the ONIX adapters to route directly to the configured `target` URL rather than performing a DeDi registry lookup.

**Rationale:**
- Enables a complete Beckn protocol flow entirely within the Docker bridge network without external dependencies.
- Eliminates latency from two DeDi registry round-trips per transaction.
- The BPP (sim-bpp) is a local simulator; registering it in a live DeDi registry is not meaningful in development.
- Switching to a real Beckn network requires only changing `targetType: bap`/`bpp` and setting the correct `registryUrl` in the YAML files — no code changes.

**Consequences:**
- Positive: Self-contained development environment; full Beckn lifecycle testable offline.
- Negative: The DeDi trust model (BPP identity verification via registry) is bypassed in development. Attackers on the Docker network could respond to Beckn messages without being registered. This is acceptable in a dev environment but must be reverted before any deployment that handles real procurement data.
- Production note: The config README documents the exact 3-step production procedure for switching to DeDi and rotating key material.

(Source: `config/README.md` -- Confidence: High)

## ONIX Schema Validator Pin at Commit d43ec30d

**Status:** Active constraint, documented in config README.

**Context:**
The ONIX adapter (`fidedocker/onix-adapter`) embeds a Beckn schema validator compiled as a `.so` plugin (`/app/plugins/schemav2validator.so`). The validator enforces the Beckn v2 wire shape on every request and response. A bug was introduced in a later commit to the ONIX repository: the `$ref` resolution logic for `SignatureHeader` and `AckSignatureHeader` schemas was broken, causing all signed Beckn messages to fail validation even when the signature and payload are correct.

(Source: `config/README.md` -- Confidence: High)

**Decision:**
Pin the ONIX adapter image to the last known-good commit `d43ec30d` in the `fidedocker/onix-adapter` Docker image reference. Do not upgrade to any later ONIX commit without first running a full end-to-end signing test covering discover → select → init → confirm → status with ED25519-signed payloads.

**Rationale:**
- The signing validation regression causes 100% of Beckn transactions to fail with a schema error. There is no configuration workaround — it is a binary in the compiled `.so` plugin.
- The fix cost of pinning is zero; the cost of an incorrect upgrade is all Beckn traffic breaking silently at the ONIX layer.
- The validator binary is not a JSON schema file and cannot be patched at runtime; diagnosing failures requires probing with intentionally malformed payloads to discover which sub-schemas are loaded (per Bap-1/CLAUDE.md wire-shape gotcha #6).

**Consequences:**
- Positive: Stable, known-good schema validation with correct ED25519 signature handling.
- Negative: New Beckn schema features and bug fixes in ONIX upstream are not available until the pin is updated.
- Negative: The `$ref` bug may be fixed in a future upstream commit; someone must periodically test newer ONIX versions against the full signed-transaction flow before updating the pin.

(Source: `config/README.md` -- Confidence: High)
(Source: `Bap-1/CLAUDE.md` wire-shape gotcha #6 -- Confidence: High)

## Vendor-Neutral ERPAdapter `typing.Protocol`

**Status:** Implemented in Phase 3 (erp-adapter service).

**Context:**
The ERP integration must support SAP S/4HANA (OData v2), Oracle ERP Cloud (REST), and a mock stub for development without requiring changes to the orchestrator or the budget-gate logic when the vendor changes. Vendor-specific API shapes diverge significantly: SAP uses OAuth2 client credentials + CSRF tokens + OData POSTs; Oracle uses OAuth2 client credentials + REST JSON POSTs; the mock uses simple HTTP endpoints.

(Source: `services/erp-adapter/README.md` -- Confidence: High)

**Decision:**
Define `ERPAdapter` as a `typing.Protocol` with six methods: `check_budget`, `push_po`, `get_po_status`, `evaluate_policy`, `get_health`, and `get_vendor_name`. Each vendor (SAP, Oracle, mock) implements the protocol in a separate module under `services/erp-adapter/adapters/<vendor>.py`. A factory function in `adapters/factory.py` selects the active adapter(s) based on the `ERP_VENDORS` environment variable (`mock`, `sap`, `oracle`, or `sap,oracle` for multi-vendor).

**Rationale:**
- Structural subtyping (Protocol) enforces the contract without inheritance, keeping vendor implementations decoupled.
- Adding a new vendor (e.g., Microsoft Dynamics) requires only: implement the six-method Protocol, add the vendor to `factory.py`, and add env vars to `config.py` and `docker-compose.yml`. The orchestrator, budget-gate logic, and webhook routes require no changes.
- Per-vendor circuit breakers (pybreaker) can be instantiated independently per adapter instance, providing vendor-level fault isolation.

**Consequences:**
- Positive: Clean extension point; new vendor adapters do not risk regressions in existing vendor paths.
- Positive: The mock adapter (`ERP_VENDORS=mock`) allows full ERP flow testing without any SAP or Oracle credentials.
- Negative: Protocol-based dispatch means type errors in vendor implementations are caught at call time rather than at class definition time (Python's structural subtyping is not enforced at import time without a type checker).

(Source: `services/erp-adapter/README.md` -- Confidence: High)

## asyncio-First + Fire-and-Forget for Non-Critical Writes

**Status:** Project-wide convention, documented in CLAUDE.md.

**Context:**
The orchestrator pipeline has a critical latency path (NL query → discover → score → select → present result) and a set of non-critical side-effects (persist audit events, write agent memory, sync to ERP) that must not stall the user-facing response. Blocking on every database write during the critical path would add tens to hundreds of milliseconds of latency per step.

(Source: `CLAUDE.md` conventions section -- Confidence: High)

**Decision:**
All non-critical writes use fire-and-forget `asyncio.create_task(...)` patterns. Three conventions are enforced project-wide:

1. **Never `await` non-critical side effects inline.** `_persist_audit()`, `_persist_memory()`, and `_persist_erp_sync()` are wrapped in `asyncio.create_task`.
2. **Never use `time.sleep()` to flush tasks.** `time.sleep()` blocks the event loop, preventing the just-created task from executing. Use `await asyncio.sleep(0)` to yield control.
3. **Fire-and-forget never raises.** Persistence helpers catch all exceptions internally and log them; the pipeline continues regardless of persistence failures.

**Rationale:**
- The critical path P95 target is under 5 seconds. Database writes for audit events and memory vectors add 50–200 ms each. On a pipeline with 5+ write points, blocking on every write would alone consume the entire SLA budget.
- Audit events and memory records are observability/learning data; losing one event due to a transient DB connection failure is acceptable and recoverable. Blocking the user for a DB write that may fail is not.
- The `time.sleep` prohibition is particularly important: it was discovered empirically that `time.sleep(0.1)` in a test to "let the task run" does not work — the task never executes because `time.sleep` blocks the thread, preventing the event loop from scheduling the coroutine.

**Consequences:**
- Positive: Pipeline latency is not bounded by database write throughput.
- Negative: Audit and memory writes can be lost if the service crashes between task creation and task completion. The audit trail is therefore eventually consistent, not immediately consistent.
- Negative: Test code that tries to assert on fire-and-forget side effects must use `await asyncio.sleep(0)` (or multiple yields) to allow tasks to execute before assertions.

(Source: `CLAUDE.md` conventions and "What NOT to do" sections -- Confidence: High)
(Source: `services/orchestrator/src/workflow.py`, code findings -- Confidence: High)

## on_discover Split Routing (Dedicated Endpoint)

**Status:** Feature beyond spec, required by ADR-0001.

**Context:**
ONIX's generic `BAPReceiver` configuration routes all `on_*` callback actions to a single base URL (e.g., `http://beckn-bap-client:8002/bap/receiver`), appending the action name automatically. This means `on_discover`, `on_select`, `on_init`, `on_confirm`, and `on_status` callbacks all arrive at `/bap/receiver/on_discover`, `/bap/receiver/on_select`, etc. For `on_discover`, the ADR-0001 Redis Pub/Sub path requires publishing to `beckn_results:{transaction_id}` before `CallbackCollector` processes the payload — but both operations must happen atomically in the handler.

(Source: `config/README.md` -- Confidence: High)
(Source: `docs/architecture/decisions/0001-use-redis-pubsub-for-async-beckn-responses.md` -- Confidence: High)

**Decision:**
Route `on_discover` to a dedicated endpoint `http://beckn-bap-client:8002` (ONIX appends `/on_discover`, resolving to `POST /on_discover`) via a separate route entry in `config/generic-routing-BAPReceiver.yaml`. All other `on_*` callbacks continue to route through the generic `http://beckn-bap-client:8002/bap/receiver` base URL. The `/on_discover` handler: (1) extracts `context.transactionId`, (2) publishes the normalized catalog to `beckn_results:{transactionId}` in Redis, (3) calls `CallbackCollector.handle_callback("on_discover", payload)` for the orchestrator path.

**Rationale:**
- `on_discover` is the only callback that participates in the Redis Pub/Sub protocol described in ADR-0001. Routing it separately makes the special handling explicit and prevents it from being changed inadvertently when the generic receiver route is modified.
- If Redis is unavailable, the handler falls through to `CallbackCollector` only (logs a warning). The MCP sidecar will time out after `REDIS_RESULT_TIMEOUT` seconds and return `found=false`, but the orchestrator path is unaffected.

**Consequences:**
- Positive: Clear separation between the Redis path (MCP sidecar) and the synchronous path (orchestrator `CallbackCollector`). Both receive `on_discover` payloads.
- Negative: ONIX routing YAML has a special case for `on_discover` that future maintainers may not understand. The comment in `config/README.md` links to ADR-0001 for context.
- Critical rule: action names must NOT be included in target URLs in ONIX routing YAMLs. ONIX appends the action automatically. `http://host:8002` + action `on_discover` resolves to `http://host:8002/on_discover`. Including `/on_discover` in the target URL would produce `http://host:8002/on_discover/on_discover` and route to a 404.

(Source: `config/README.md` -- Confidence: High)
(Source: `services/beckn-bap-client/README.md` -- Confidence: High)

## sim-bpp Replacing sandbox-2.0

**Status:** Implemented as-built deviation from spec.

**Context:**
The original design used `fidedocker/sandbox-2.0` as a local BPP simulator. `sandbox-2.0` had a fixed, hardcoded catalog that could not be changed without rebuilding the image. It did not support order lifecycle simulation (auto-advance from ACCEPTED to DELIVERED) or fine-grained catalog matching control.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)

**Decision:**
Replace `sandbox-2.0` with `sim-bpp`, a custom Node.js BPP simulator (port 3002). Key design choices:

- **Hot-reload catalog:** `catalog.json` is bind-mounted at runtime. Changes take effect on the next request without container rebuild.
- **Full Beckn action coverage:** supports all 10 Beckn actions (discover, select, init, confirm, status, track, update, cancel, rate, support).
- **Auto-advance lifecycle:** when `SIM_BPP_AUTO_ADVANCE=true`, confirmed orders automatically transition ACCEPTED → PACKED → SHIPPED → OUT_FOR_DELIVERY → DELIVERED at configurable intervals, with each transition published to Kafka and PATCHed to data-normalizer.
- **AND-token catalog matching:** prevents false positives on over-broad queries (see next decision).

**Rationale:**
- Development realism: a mutable catalog enables testing different product categories, pricing scenarios, and stock levels without code changes.
- End-to-end testing: the auto-advance lifecycle simulates real order fulfillment, enabling real-time notification and WebSocket tracking tests without manual intervention.
- The BAP code is written against standard Beckn v2 wire shapes; when porting to a real Beckn network, `sim-bpp` is removed and the ONIX routing target changes — the BAP requires no code modifications.

**Consequences:**
- Positive: Self-contained, modifiable BPP for development and testing. Auto-advance enables notification-dispatcher and WebSocket tracking tests.
- Positive: The BAP layer is truly network-agnostic; the same BAP code runs against `sim-bpp` in development and a real Beckn network in production.
- Negative: `sim-bpp` is a Node.js service added to the Docker Compose stack, adding one more dependency and startup time.
- Note: `docker-compose.yml` sets `SIM_BPP_AUTO_ADVANCE=true` by default, meaning all orders in the Docker stack will auto-advance through the lifecycle unless explicitly disabled.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)
(Source: `services/sim-bpp/README.md` -- Confidence: High)

## AND-Token Catalog Matching in sim-bpp

**Status:** Feature beyond spec, implemented in sim-bpp.

**Context:**
Beckn discovery queries are natural-language fragments (e.g., "500 reams A4 paper 80gsm Bangalore 3 days"). Naive substring or bag-of-words matching on such queries against a product catalog returns large numbers of false positives: every item in the catalog that contains any word from the query would match. A query for "300 meters Cat6 UTP cable" should not return "A4 Paper" simply because both items have short names.

(Source: `services/sim-bpp/README.md` -- Confidence: High)

**Decision:**
Implement AND-token matching in sim-bpp's discovery handler:

1. Tokenize the query (lowercase, apply light singularization).
2. Compute the catalog vocabulary: all tokens appearing in any item's name or keyword list.
3. Discard any query token that has no match anywhere in the catalog vocabulary (these are filler words, quantities, or location names that carry no product-discriminating signal).
4. Require that ALL remaining filtered tokens appear in the matched item's name or keywords.
5. Return only items passing the AND predicate.

**Rationale:**
- Reduces false positives: a query for "Cat6 UTP cable" will match networking items but not "A4 Paper" even if both are in the catalog.
- Discarding unrecognized tokens (quantities like "500", locations like "Bangalore") prevents them from eliminating all results because they appear in no item's metadata.
- The trade-off is a slightly more brittle match: misspelled query terms that are not in the catalog vocabulary are silently dropped. For a development simulator with a known, controlled catalog this is acceptable.

**Consequences:**
- Positive: Discovery results are significantly more relevant; the scoring step operates on a pre-filtered set.
- Negative: Queries containing product names that differ from catalog vocabulary (plurals, brand variations, abbreviations) may return zero results. The catalog must be designed with vocabulary coverage in mind.
- Negative: This matching logic is specific to sim-bpp. A real Beckn network's BPPs will have their own (potentially different) matching semantics.

(Source: `services/sim-bpp/README.md` -- Confidence: High)

## Dual-Secret HMAC Rotation for ERP Webhooks

**Status:** Feature beyond spec, implemented in Phase 3 (erp-adapter).

**Context:**
ERP vendors (SAP, Oracle) sign their inbound webhook payloads with an HMAC-SHA256 shared secret. Rotating the shared secret — necessary for security hygiene and mandatory after any suspected compromise — typically requires a brief window where the old secret is invalid but the new secret has not yet been propagated to the vendor. During this window, legitimate webhook deliveries are rejected.

(Source: `services/erp-adapter/README.md` -- Confidence: High)

**Decision:**
Each vendor maintains two HMAC secrets: a primary (`{VENDOR}_WEBHOOK_HMAC_SECRET`) and a "next" secret (`{VENDOR}_WEBHOOK_HMAC_SECRET_NEXT`). The webhook handler in `erp-adapter` validates an incoming signature against the primary secret first; if that fails, it validates against the `_NEXT` secret. Either match accepts the webhook.

Rotation procedure: (1) generate a new secret and populate `_NEXT`; (2) configure the vendor's outbound webhook to use the new secret; (3) after all in-flight deliveries using the old secret have been received, promote `_NEXT` to the primary and clear `_NEXT`.

**Rationale:**
- Zero-downtime secret rotation: during the transition window, `erp-adapter` accepts webhooks signed with either the old or the new secret.
- No coordination window required between Infosys ops and the vendor's webhook delivery system.
- Standard dual-key rotation pattern (analogous to JWT key rotation) with no custom protocol.

**Consequences:**
- Positive: Secret rotation does not require any maintenance window or webhook-delivery gap.
- Negative: During the rotation window, both secrets are valid simultaneously. If the old secret is compromised, rotating it still requires a brief period where the compromised secret is honored (until all in-flight deliveries using it complete). This window should be minimized by setting a short delivery retry window on the vendor side.

(Source: `services/erp-adapter/README.md` -- Confidence: High)

## Per-Vendor Circuit Breakers (pybreaker)

**Status:** Feature beyond spec, implemented in Phase 3 (erp-adapter).

**Context:**
`erp-adapter` connects to external ERP vendor APIs (SAP S/4HANA, Oracle ERP Cloud, or the mock stub) for synchronous budget checks (≤800 ms hard timeout) and asynchronous PO push operations. Vendor APIs can become temporarily unavailable due to scheduled maintenance, overload, or network issues. Without circuit breakers, every failing API call blocks for its full timeout, and a wave of failing calls can exhaust the outbox worker thread pool.

(Source: `services/erp-adapter/README.md` -- Confidence: High)

**Decision:**
Instantiate one `pybreaker.CircuitBreaker` per configured vendor adapter. Configuration:
- `BREAKER_FAIL_MAX = 5` (trips to OPEN after 5 consecutive failures)
- `BREAKER_RESET_TIMEOUT_SECS = 60` (auto-probes after 60 seconds in OPEN state)

The breaker wraps both `check_budget` and the outbox worker's vendor API call. When a breaker is OPEN, budget checks fail immediately (subject to `ERP_BUDGET_CHECK_REQUIRED` fail-closed flag) rather than waiting for the timeout.

**Rationale:**
- Vendor outages should not cascade into a full procurement pipeline stall. With a circuit breaker, the first five failures absorb the timeout latency; all subsequent calls during the OPEN period fail instantly.
- `ERP_BUDGET_CHECK_REQUIRED=true` (fail-closed) combined with a circuit breaker means an open breaker will block commits until the vendor recovers — this is the correct behaviour for a budget gate.
- `ERP_BUDGET_CHECK_REQUIRED=false` (fail-open) allows commits to proceed without a budget check when the ERP is down. This is available for development (`docker-compose.yml` sets `ERP_BUDGET_CHECK_REQUIRED=false`).
- `GET /readyz` exposes per-vendor breaker state, enabling Kubernetes/Prometheus health monitoring.

**Consequences:**
- Positive: Vendor API failures fail fast after the first five; pipeline throughput is preserved during partial outages.
- Positive: Breakers recover automatically via probe after `BREAKER_RESET_TIMEOUT_SECS` seconds without operator intervention.
- Negative: `BREAKER_FAIL_MAX=5` means the first five failures each block for up to `BUDGET_CHECK_TOTAL_TIMEOUT_MS=800` ms before contributing to the trip count. Total worst-case latency to trip: 4 seconds.

(Source: `services/erp-adapter/README.md` -- Confidence: High)

## Docker Compose Instead of Kubernetes (Phases 1–3)

**Status:** Implemented as-built deviation from spec; Kubernetes is Phase 4 scope.

**Context:**
The original design specified Kubernetes (EKS/AKS/GKE) with Helm charts and ArgoCD GitOps for all phases of the project. This requires: a Kubernetes cluster (cloud or local minikube/k3d), Helm, ArgoCD, image registry, persistent volume provisioners for PostgreSQL and pgvector, and Kubernetes networking for service discovery.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)

**Decision:**
Use Docker Compose for all Phases 1–3 deployments. The `docker-compose.yml` at the repository root defines 18 services on a shared `beckn_network` bridge. Services communicate via Docker DNS names (e.g., `http://data-normalizer:8006`). The main PostgreSQL database runs natively on the developer host (not in Docker) and is reached by containers via `host.docker.internal:5432`. A separate `negotiation` PostgreSQL container (port 55432) serves only the negotiation engine's LangGraph checkpoint store.

**Rationale:**
- Phases 1–3 are development and pilot phases. Kubernetes adds cluster management overhead (RBAC, networking policies, storage classes, pod scheduling) that provides no value when all services run on a single developer laptop.
- `docker compose up -d` is a one-command startup with sub-minute cold-start time. A Kubernetes-based startup would require a cluster, Helm releases, and ArgoCD sync cycles.
- Docker Compose is sufficient to prove the full Beckn lifecycle; the service code is written with environment-variable-driven URLs and is cluster-agnostic.
- Kubernetes (EKS/AKS/GKE) with Helm and ArgoCD is explicitly the Phase 4 production-readiness deliverable, alongside OWASP pen test, 80% integration test coverage, and P95 latency validation.

**Consequences:**
- Positive: Fast iteration cycle. Any service can be rebuilt and restarted independently with `docker compose up -d --build <service>`.
- Negative: No horizontal scaling, no rolling updates, no pod health-based restarts in Phases 1–3. A service crash requires manual `docker compose restart`.
- Negative: The `orchestrator` service publishes both host ports 8000 and 8004, a workaround for frontend `.env.local` defaults that would be unnecessary in Kubernetes (services would use cluster DNS).
- Negative: `negotiation-engine` exposes host port 18004 (not 8004) to avoid conflict with orchestrator on the developer host — another workaround that Kubernetes service namespacing would eliminate.
- Note: `services/claude_openai_proxy/` (the Claude Code CLI proxy used by negotiation-engine and demo-gateway) is explicitly not Dockerized. It must run natively on the host with the `claude` binary installed, and binds to loopback + docker bridge via a systemd unit file (`claude-proxy.service`). It will require special handling when moving to Kubernetes.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)

## 384-dim Embeddings Instead of 3072-dim

**Status:** Implemented as-built deviation from spec.

**Context:**
The original design specified OpenAI `text-embedding-3-large` (3072 dimensions) as the embedding model for both the BPP catalog semantic cache and agent memory vectors. Using a cloud embedding API introduces per-call cost, network dependency, and data egress of catalog and procurement data. The 3072-dimension vectors also impose significant pgvector HNSW index build time and memory cost.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)

**Decision:**
Replace `text-embedding-3-large` with two local embedding models, both at 384 dimensions:

- **`all-MiniLM-L6-v2`** (sentence-transformers, ~90 MB) — used by IntentParser Stage 3 (BPP catalog semantic cache, table `bpp_catalog_semantic_cache`) and data-normalizer memory endpoints. Downloaded from Hugging Face Hub on first startup; cached in memory thereafter.
- **`BAAI/bge-small-en-v1.5`** (fastembed ONNX runtime, ~65 MB) — used by data-normalizer for agent memory write/search (table `agent_memory_vectors`). fastembed chosen specifically to avoid adding the ~1.5 GB PyTorch dependency to the data-normalizer container.

Both models produce `vector(384)` outputs and use HNSW cosine indexing in pgvector. The similarity threshold for agent memory retrieval is 0.75; items below this threshold are excluded from the reasoning panel.

**Rationale:**
- Zero per-call cost: both models run entirely locally via ONNX or sentence-transformers.
- No data egress: procurement data (catalog descriptions, order histories) never leaves the developer machine.
- For the pilot corpus (< 100 K records), 384-dim models achieve quality comparable to 3072-dim models on the structured procurement vocabulary used in catalog descriptions and order summaries.
- fastembed ONNX avoids a multi-gigabyte PyTorch installation in a container whose primary job is database writes.

**Consequences:**
- Positive: Zero embedding cost, offline operation, sub-100 ms embedding inference after warm-up.
- Positive: HNSW index build and query are significantly faster on 384-dim vectors versus 3072-dim.
- Negative: 384-dim models have lower semantic precision on ambiguous or cross-domain queries compared to `text-embedding-3-large`. This matters most when procurement items have ambiguous names. The 0.75 similarity threshold mitigates false matches.
- Negative: First embedding call after container start incurs a 10–30 second cold-start while the ONNX model is loaded into memory.
- Known schema bug: `database/sql/00_extensions_and_types.sql` defines `embedding_model_type` ENUM with only `'text-embedding-3-large'` and `'e5-large-v2'`. Migration `22_agent_memory_vector_dim.sql` adds `'all-MiniLM-L6-v2'` but never adds `'BAAI/bge-small-en-v1.5'`. Any code that attempts to store the BAAI model name in the `embedding_model` column (type `embedding_model_type`) will fail with a PostgreSQL invalid enum value error. The column default in `15_agent_memory_vectors.sql` is also never updated from `'text-embedding-3-large'` to `'all-MiniLM-L6-v2'` in the migration.

(Source: `KnowledgeBase/project_scaffold/implementation_deviations.md` -- Confidence: High)
